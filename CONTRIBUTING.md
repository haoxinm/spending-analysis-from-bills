# Contributing

## Development setup

```console
$ uv python install 3.12        # if you don't already have it
$ uv sync --extra dev            # Python deps into .venv/
$ cd frontend && npm ci           # frontend deps
```

Development works on Windows, macOS and Linux (CI runs the Python tests on all three). The
commands above are identical everywhere; on Windows use PowerShell or Git Bash, and
`uv run <cmd>` rather than activating the virtualenv by hand (or run
`.venv\Scripts\Activate.ps1`). Install Node.js 22+ only if you touch `frontend/` or build a wheel.
Set `PYTHONUTF8=1` if you see encoding errors reading fixtures on Windows. The tests never touch a
real credential store (`keyring` is mocked) or your real data directory (`SPEND_ANALYZER_HOME` is
redirected per test), so no keyring backend is needed just to run the suite. When writing code,
build paths with `pathlib` (never string-splitting on `/`), open text files with an explicit
`encoding="utf-8"`, and don't rely on POSIX permission bits (`chmod`) or on replacing a file that
may be open — mark genuinely POSIX-only tests with
`@pytest.mark.skipif(sys.platform == "win32", reason=...)`.

## Testing LLM code

No test makes a network call. `tests/llm_fakes.py` provides `FakeLLM`, which replaces
`spend_analyzer.llm.client._post`, records every request body, URL and header, and answers in
whichever wire format the config asks for (`openai_chat`, `openai_responses`,
`anthropic_messages`). Use `install(monkeypatch, fake)` to swap it in, `remote_cfg(...)` for an
`LLMConfig` pointing at a fake remote host, and queue replies (a string, a `(status, body)` tuple, or
a callable) with `FakeLLM.queue`. Assert on `fake.requests` to check exactly what would have been
sent — that is how the egress and redaction guarantees are tested. See `tests/llm/`,
`tests/classify/test_egress.py` and `tests/test_cli_llm.py` for examples. Architecture rules (only
`llm/client.py` imports an HTTP client; only the two egress seams import it) are enforced by
`tests/test_architecture_guards.py`.

## Checks

Run all of these before submitting a change — CI runs the same commands:

```console
$ uv run ruff check
$ uv run ruff format --check
$ uv run mypy --strict src
$ uv run pytest -q

$ cd frontend
$ npx tsc --noEmit
$ npx eslint .
$ npx vitest run
$ npx playwright test          # one happy-path e2e: import fixture -> classify (mocked LLM) -> chart
```

Whole-suite `pytest` must stay green after your change, not only the tests you added.
`mypy --strict` applies to `src/`; test code is not required to satisfy it.

## Fixture rules

**Never commit a real bank/card statement, a `.db` file, or a secret.** This is enforced by a
pre-commit hook (`scripts/check_no_statements.py`) that rejects any `.pdf` outside
`tests/fixtures/generated/` and any path that looks like a real statement filename, and by
`.gitignore` blocking `*.pdf`, `*.db`, and `.env` outright.

- **Fixtures are synthetic only**, generated by a `LayoutBuilder` under `tests/fixtures/gen/` and
  written by `tests/generate_fixtures.py` to `tests/fixtures/generated/<layout_id>/*.pdf` plus a
  matching `.json` golden. Regenerate with:

  ```console
  $ PYTHONPATH=. uv run python tests/generate_fixtures.py
  ```

  The repository root must be on the import path (the script imports `tests.fixtures.gen`), hence
  `PYTHONPATH=.` (PowerShell: `$env:PYTHONPATH = "."` first). `uv run python -m tests.generate_fixtures`
  works without it.

- **Generation is deterministic.** A given `LayoutBuilder` variant always produces byte-for-byte
  the same PDF and golden, so a diff in `tests/fixtures/generated/` after a code-only change is a
  sign something is wrong, not an expected side effect.
- **Invented bank names only.** No real bank, card issuer, or account holder's name appears in any
  fixture, test, or docstring — issuer identity is user data (§2f.4 of the design doc), never a
  hard-coded string in the codebase.
- **Never hand-edit a generated `.pdf` or `.json`.** Change the `LayoutBuilder` and regenerate.
- **Tax fixtures use invalid identifiers and invented names.** A tax form carries SSNs and EINs, so
  every `tests/fixtures/gen/tax_*.py` builder takes its identities from `tax_common.py`: SSNs in
  the never-issued `9xx` area (for example `912-34-5678`), EINs with the unassigned `99-` prefix,
  fictional person, employer, bank and broker names, and no real institution (no real bank, broker
  or employer, and no real address). Never paste identifiers from a real form, even redacted. The
  tripwire `tests/fixtures/test_tax_fixture_hygiene.py` fails on a valid-looking SSN or EIN or a
  denylisted institution name in a generator or a generated file, and a tax builder's `layout_id`
  must equal its module name (`tax_w2.py` -> `tax_w2`).

## Adding a parser

This is the most likely contribution. A new layout needs, and needs only:

1. **One parser file** under `src/spend_analyzer/ingest/parsers/`, implementing the
   `StatementParser` protocol (`src/spend_analyzer/core/types.py`): an `id`, a `detect()` that
   scores a document by *structure* (never by bank name), and a `parse()` that returns a
   `ParsedStatement`. Reuse the shared primitives in `ingest/layout.py` for money parsing, row
   clustering, column bands, and year inference — never parse money or dates ad hoc.
2. **One `LayoutBuilder`** under `tests/fixtures/gen/`, describing synthetic statement variants
   (a clean one, one with a foreign-currency line, one with a multi-line description, one that
   exercises the sign of a purchase/refund/payment) for `tests/generate_fixtures.py` to render.
3. **One golden set** — the `.json` files `generate_fixtures.py` writes alongside each PDF,
   asserting the exact `ParsedStatement` your parser should produce, including transaction sign
   (I5: positive = money leaving the user — assert this per transaction kind, not just on a total,
   which can hide a matched pair of sign flips).
4. **One row in the cross-`detect()` matrix**, `tests/ingest/test_cross_detect.py`: your parser
   must score its own fixtures above the registry's threshold (`0.5`) and every *other* layout's
   fixtures at or below it, and `registry.select()` must actually route your fixtures to your
   parser. This is what catches a `detect()` that's accidentally lazy (firing on a generic word
   like "Date" or "Amount").

No shared file needs editing to register a new parser — `registry.py` discovers parsers by module
scan, and `tests/generate_fixtures.py` discovers builders by package scan — so independent parser
contributions don't conflict with each other on one file.

If a statement's shape doesn't warrant a new built-in parser at all (a one-off bank, a personal
account), see [docs/LAYOUTS.md](docs/LAYOUTS.md#anything-else-the-generic-parser-and-layout-specs)
for the no-code layout-spec path instead — it needs no PR.

## Adding a tax-form parser

Tax forms (W-2, 1099, 1040) have their own parser family, registry and fixtures, deliberately
separate from statement parsers (see [docs/TAX.md](docs/TAX.md) for what the existing ones read).
A new form needs:

1. **One parser module** under `src/spend_analyzer/ingest/tax/parsers/` exposing a module-level
   `PARSER` object that satisfies the `TaxFormParser` protocol (`core/tax_types.py`): `id`,
   `version`, `form_types`, `detect(doc)` (a structure-based score in [0, 1]; it must never raise)
   and `parse(doc, *, tax_year=None)` returning a `ParsedTaxDocument`. A module whose name starts
   with `_` is skipped, and `ingest/tax/registry.py` discovers `PARSER` by module scan, so nothing
   else needs registering. There is no generic fallback: a document no parser scores above `0.5`
   is `unsupported`.
2. **Reuse the shared primitives**: `ingest/tax/fields.py` for labelled-amount lookup (its module
   docstring is the API), `ingest/tax/common.py` (`require_year`, `sanitize_payer_name`,
   `build_document`), `ingest/tax/year.py` and `ingest/tax/tin.py`. Money goes through
   `ingest/layout.parse_money`; never parse amounts ad hoc.
3. **Map every box to a category**, using only the vocabulary in `core/tax_types.py`
   (`IncomeCategory`, `TaxCategory`). Amounts are integer cents; only the two capital-gain
   categories may be negative. Mark items that are inside another line (qualified dividends,
   tax-exempt interest) `is_memo=True`. Declare whether the form is a *source* or a *return* in
   `FORM_ROLE`, because that decides how it is aggregated.
4. **Never let an identifier through.** Read a taxpayer identifier only via `tin.mask_tin` and keep
   the last four digits; pass anything that could be echoed (payer names, labels, warnings, error
   messages) through `tin.scrub` / `common.sanitize_payer_name`, and keep warnings free of document
   text and of digit runs of six or more. Never read the recipient's name, address or number.
5. **One `LayoutBuilder` under `tests/fixtures/gen/tax_<form>.py`** with a `layout_id` equal to the
   module name, built from `tax_common.py` (see the fixture rule above) and covering at least a
   normal form, a zero or missing-box case, a corrected form where the form has one, and a case
   that must be rejected. `PYTHONPATH=. uv run python tests/generate_fixtures.py` renders them.
6. **Goldens** are written beside each PDF as `.json`; the parser tests in `tests/ingest/tax/`
   compare against `tests/ingest/golden/tax/<layout_id>/`. Add a parser test file next to the others
   and assert both the categories and the amounts, including signs.
7. **One row in the cross-`detect()` matrix**, `tests/ingest/tax/test_cross_detect.py`: your parser
   must score its own fixtures above the threshold and every other tax parser's fixtures and every
   bank fixture at or below it (`test_every_tax_parser_has_fixtures` fails for a parser without
   fixtures).

If the form changes layout between years (1040 lines are renumbered), keep a per-year field table
and warn rather than guess for an unlisted year, as `parsers/f1040.py` does. New federal bracket
data goes in `ingest/tax/data/federal_brackets.yaml`, copied from the IRS revenue procedure named
in its header and checked against the IRS publication.

## Adding a layout spec

A layout spec is the declarative (YAML), no-code alternative to a parser file — produced by the
web UI's layout mapper, or written by hand and validated the same way. See
`src/spend_analyzer/ingest/layout_spec.py` and `layout_spec.schema.json` for the format, and
`tests/ingest/test_layout_spec.py` / `tests/ingest/specs/` for worked examples. A spec is
validated against the JSON Schema and every regex in it is length-capped and screened for
catastrophic backtracking before it is ever run — a spec is untrusted input even once approved, so
a change to the format or the interpreter must keep both checks.

## Code style

Full type annotations, `mypy --strict`. Frozen dataclasses for data, Pydantic at I/O boundaries
only. No mutable default arguments. Public functions document units, sign conventions, and raised
exceptions — a subtle sign error in this codebase costs a user real money in a report. Never catch
bare `Exception` in library code, and never swallow `EgressViolation`.

## Security-sensitive changes

Anything touching `classify/llm/`, `llm/` (the HTTP client and the statement parser), `api/security.py`, the upload path in
`api/routers/statements.py`, or `analytics/query.py` is security-sensitive by nature of this
project's privacy model. So is the tax feature (`ingest/tax/`, especially `tin.py` and
`pipeline.py`, plus `analytics/tax_query.py`, `api/routers/tax.py` and `core/tax_types.py`) and the
net-worth feature (`analytics/net_worth_query.py`, `api/routers/net_worth.py`,
`api/services/net_worth.py`): they hold taxpayer identifiers and account balances, must not import an
LLM or HTTP client (`tests/test_architecture_guards.py`), and must keep full identifiers out of the
database, logs and extract cache — see [docs/SECURITY_REVIEW.md](docs/SECURITY_REVIEW.md) for the checklist
those areas are held to, and [SECURITY.md](SECURITY.md) to report a vulnerability rather than
opening a public issue.
