# Security review (P4-E)

This re-verifies every item of the plan's §6.4 security checklist and every invariant in §1.1
against the **shipped code**, not the plan text. Evidence cites the actual file/line or the test
that exercises it; verdicts are `pass`, `partial`, or `fail`. This review was performed by reading
the code and its existing tests; it did not modify either — any `partial`/`fail` below is reported
to the orchestrator rather than fixed here.

Run at commit reachable from `wp/P4-E`, against the full test suite (610 passed at review time).

## Invariants (§1.1)

| # | Invariant | Verdict | Evidence |
|---|---|---|---|
| I1 | No LLM ever receives raw PDF text, dates, amounts, issuer names, account identifiers, `issuer_category`, or `description_raw`; only `description_clean`, as CSV, through `egress.py`. No exception for local models. | **pass** | `classify_batch(descriptions: list[str], ...)` (`egress.py:150`) takes only pre-normalized description strings from its caller and builds a two-column `id,description` CSV (`build_csv`, `egress.py:80`) — no other field is ever assembled into the payload. Caller discipline (only `description_clean` is passed in) is enforced by `cascade.py`, which is the only caller (`grep -rn classify_batch src/` → `egress.py` def, `cascade.py` call site, `settings.py`'s connectivity test with a literal test string). No branch conditions on `cfg.mode`/provider change what's sent — the same `build_csv`/`assert_safe` path runs for local (`api_base` override) and remote providers alike. |
| I1b | Local-only set (`accounts.mask`, `accounts.issuer_id`, `issuers.{name,slug,match_terms}`, `transactions.{description_raw,issuer_category}`, `users.{name,pii_aliases}`, statement file paths, extracted page text) never egressed by any path. CI-enforced grep on `classify/llm/`. | **pass** | Same evidence as checklist item 6, plus: statement file paths and extracted page text are handled entirely in `ingest/` (item 18's CI guard: no HTTP client there at all) and never passed into `classify/llm/`'s call sites — `cascade.py` passes `description_clean`/`merchant_key` values, not paths or raw page text, into `classify_batch`. |
| I2 | Exactly one module may `import litellm`. CI-enforced with `ast`. | **pass** | Checklist item 17. |
| I3 | `ingest/` imports no HTTP client, ever. CI-enforced. | **pass** | Checklist item 18. |
| I4 | Every transaction has exactly one category and one subcategory; never a category with a null subcategory. | **partial** | `db/models.py`'s `Transaction.category_id`/`subcategory_id` are both nullable at the schema level (needed for the pre-classification/`needs_review` state), so the invariant is a *business* rule enforced by the classification cascade (`cascade.py`) and, per `tests/db/test_schema_parity.py`, checked structurally — but I found no runtime assertion or CI check that rejects a write setting `category_id` non-null with `subcategory_id` null (or vice versa) outside of the cascade's own code paths (e.g. a hand-written migration, a future direct `session.add(Transaction(...))` elsewhere, or a bug in a not-yet-written caller). **Finding**: no single choke point (a DB `CHECK` constraint, or a model-level validator) enforces "category and subcategory are both set or both null" independent of every caller remembering to do so correctly. **Suggested fix**: add a SQLite `CHECK ((category_id IS NULL) = (subcategory_id IS NULL))` constraint on `transactions` in a follow-up migration, or a SQLAlchemy `@validates`/event listener on `Transaction`, so the invariant holds even if a future write path forgets it. |
| I5 | Amounts are signed integer minor units; positive = outflow; applied at parse time per parser; every parser has a sign test. | **pass** | Verified per-parser: `tests/ingest/test_layout_a.py`, `test_layout_b.py`, `test_layout_c.py`, `test_layout_d.py`, and `test_generic_parser.py` each assert the sign of a purchase, refund, and payment explicitly (grepped for `amount_minor` assertions with both positive and negative expected values in each file). `layout.parse_money` (`ingest/layout.py`) is the single money-parsing function all four layouts and the generic parser use. |

Exercised by `tests/classify/test_cascade.py`. |
| I7 | Secrets live only in Keychain; never DB, `config.toml`, or logs. | **pass** | Checklist item 16. |

| I9 | Re-importing a byte-identical file is a no-op; an overlapping-period import creates no duplicate rows. | **pass** | `_save_upload` writes to `<sha256>.pdf` so a byte-identical re-upload lands on the same path (`statements.py:44-52`); `gateway.propose_import` matches on `file_sha256` (referenced in `statements.py`'s own docstring, `statements.py:48`) to report the existing statement rather than re-parsing. Dedupe on insert uses `INSERT ... ON CONFLICT DO NOTHING` against `(account_id, dedupe_hash)` (`pipeline.py`'s `_insert_transactions`, `pipeline.py:661-`), with `dedupe_hash` derived from `(account_id, posted_date, amount_minor, description_raw, occurrence_index)` — overlapping-period rows land on the same conflict key and are skipped, not duplicated. Exercised by `tests/classify/test_kinds.py` and `tests/ingest/test_layout_d.py`. |

## Summary

Of 22 checklist items (20 applicable to v1, 2 marked n/a as Phase 5-only) and 11 invariants: **31
pass outright, 2 partial (I4, I10), 0 fail.** Neither partial is an active data leak or a broken
security control — both are "no single enforced choke point for a business-logic invariant that
every current caller happens to respect" (I4) and "confidence is recorded per-item rather than
per-batch, which may or may not be what the plan's wording intended" (I10) — but both are reported
above with a concrete file and a suggested fix per the P4-E brief, for the orchestrator to dispatch
if desired rather than fixed in this review.
